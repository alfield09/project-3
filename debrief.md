### Vocabulary

1. User-centered design (critical): Making and revising product decisions around the needs, circumstances, and experience of the people who will use it. The Client's goals and the Developer's preferences do not by themselves establish that it is usable.

2. Context of use (critical): The circumstances in which someone uses a product, including their goal, environment, device, and constraints. These circumstances help explain why a design choice matters.

3. User story (critical): A concise description of who needs something, what they want to accomplish, and why. It expresses a need or outcome rather than prescribing a particular interface.

4. Scope and feature creep: Scope defines what the project includes and excludes. Feature creep is expansion beyond that scope without deliberate decisions about priorities, time, and consequences.

5. Evidence and source credibility (critical): Evidence supports or challenges a claim. Credibility depends on the source's relevant expertise, methods, limitations, and support for the particular use. An Agent's confident summary or a citation alone does not verify a claim.

6. Specification versus implementation plan (critical): The specification defines the intended result and requirements; the plan defines the ordered route and checkpoints for building and checking it. Update the document that owns a changed decision.

7. Acceptance checks and verification (critical): An acceptance check compares an observed result with an expected result for a requirement. Verification uses such checks and supporting evidence to establish whether the work meets its requirements; an Agent's completion report is not enough.

8. API and endpoint: An API defines how software can interact with another system. An endpoint is a particular address through which an API operation is accessed, such as requesting forecast data.

9. Request and response: A request asks a service to perform an operation or supply data. Its response returns a status and may contain data or error information; receiving a response does not necessarily mean the request succeeded.

10. JSON: A text format for structured data, using objects, arrays, and values. The app must interpret the returned fields and their meaning rather than assume every expected value is present.

11. Asynchronous operations: Work whose completion is handled later while other activity can continue. Network requests may finish at different times or fail; the app must manage waiting and prevent an outdated result from replacing the currently selected one.

12. Live data versus forecast: Live data is obtained from a provider during use rather than supplied only as fixed sample values. It can include current conditions and forecasts. A forecast predicts future conditions; being retrieved live does not make it a measurement of what will happen.

13. Data mapping (critical): Connecting provider fields to the app's intended inputs, including the correct location, date, units, and meaning. A daily high and a current temperature are different inputs even if both are temperatures.

14. Conditional logic and derived recommendations (critical): Rules choose behavior according to conditions. Outfit categories and reminders are outputs derived from weather inputs and the app's rules; they are not necessarily advice supplied by the weather provider.

15. State and view (critical): State represents the app's relevant data and selections at a moment. A view presents that state to the User. Coordinated outputs should reflect the same selected location, date, conditions, and recommendation.

16. Single source of truth (critical): One authoritative place for a particular decision or value, with other uses referring to or deriving from it. Project decisions belong in the document that owns them; recommendation outputs derive from one shared recommendation state. This does not mean putting the whole project in one file.

17. Responsive design: Adapting layout and interaction to the available screen and device. A useful phone and laptop experience may need different arrangements, not just the same layout scaled down.

18. Accessibility: Designing so people with different abilities can perceive, understand, navigate, and operate the app, including with assistive technology. Relevant checks include labels, keyboard operation, focus, contrast, and alternatives to information conveyed only visually.

19. Usability testing and iteration: Observing people attempt realistic tasks to identify successes and barriers, then using that evidence to revise and check the product. Observations and interpretations are distinct; asking whether someone likes the app is not enough.

20. Deployment: Making a working version available on a host for others to access. The deployed version needs its own checks; a working local version does not prove the public URL serves the intended result.

Reference guidance for explanations: [MDN's network-request guidance](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Scripting/Network_requests) and [W3C's accessibility introduction](https://www.w3.org/WAI/fundamentals/accessibility-intro/). These support explanations and are not additional Developer deliverables.
